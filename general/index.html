Building reliable real-robot deployment infrastructure

A practical field guide
September 2026

If you are reading this, somebody has probably handed you the part of robotics that sits between “the model works” and several kilograms of hardware actually moving. Good luck. This layer is rarely glamorous, occasionally frightening, and full of bugs that sound like model failures until the logs prove otherwise.

This guide is about the engineering patterns that survive changes in models and robots: recover the training contract, establish a plain baseline, measure timing, add only the motion processing you can justify, and preserve enough data lineage to explain every executed action.

If you make a major change to timing, action semantics, recording, safety ownership, or robot integration, update the guide in the same change. The next engineer should inherit the reasoning, not perform archaeology on terminal history.

The dataset is part of the runtime specification

A finite output tensor proves very little. Two policies can both accept three images and a state vector, yet disagree about camera roles, RGB versus BGR, field order, units, prompt spelling, timestamps, and whether an action is absolute or relative.

Write those assumptions down as an executable contract. At minimum it should declare observation keys, shapes, units, camera roles, control frequency, action horizon, action semantics, task vocabulary, and normalization assets.

Working rule

When documentation, runtime defaults, and recorded data disagree, inspect the data and the exact training transforms before changing the robot runtime.

Make the plain policy move before improving it

First prove the shortest path: fresh observations enter the adapter, the service returns finite actions, the action meaning is correct, and one supervised command reaches the intended actuator. Jittery but correctly directed motion is a useful baseline. A perfectly smooth robot moving the wrong joint is not.

Do not begin with RTC, filters, splines, automatic retries, or relaxed limits. Each extra mechanism changes the evidence. Add them only after the raw policy path is understood.

  1. Verify camera identity, color, orientation, resolution, and cadence.
  2. Verify state order and units against a physical movement.
  3. Verify action order, units, and absolute/delta semantics.
  4. Measure raw action size and inference latency.
  5. Run a supervised, bounded hardware canary.

Keep policy computation separate from hardware ownership

The model service may be replaced, restarted, or moved to another machine. The hardware writer should not. Model and expert actions are candidates; a router selects one, a final safety boundary validates it, and exactly one owner sends commands.

Asynchronous inference needs elapsed-action alignment

Inference and control run on different clocks. While a request is in flight, the robot keeps consuming actions from the current queue. When the reply arrives, its leading rows describe moments that have already passed.

The general solution is simple: request before the queue is empty, measure how many control steps elapsed, discard that many rows from the new reply, then install only the future portion. A short seam blend is optional; alignment is not.

Trigger timing should come from measured latency expressed in control steps, with a small margin. Re-measure it when the model, device, image pipeline, compiler, or network changes.

Do not confuse these

Asynchronous inference prevents blocking. Alignment removes actions whose time has passed. Seam blending reduces a discontinuity between valid future actions. They solve three different problems.

Choose motion processing for the artifact you measured

“Make it smoother” is not a diagnosis. Compare raw per-step joint changes and seam discontinuities with the training data before adding a processor.

Jump only when a new chunk arrivesRTC alignment, then a short seam blendExcess blending makes every replan sluggish.
High-frequency noise inside a valid chunkCausal low-pass filterToo much filtering adds lag and may prevent reaching the target on time.

A low-pass filter should normally carry state across chunk boundaries and operate on the selected model stream before final dispatch. It should not filter expert takeover unless that is part of the collection contract.

The initial pose belongs to the data distribution

A pose that looks symmetric or convenient to a human may be out of distribution for the policy. Sample initial states from successful training episodes, cluster them if necessary, and choose representative states with clear physical feasibility.

Record the selected state, its source episode, units, and tolerances. If the robot cannot safely reach it, fix the collection or transition procedure rather than inventing a new start pose by eye.

Coverage limitation

A representative sample can select from existing coverage; it cannot create start states the demonstrations never contained.

DAgger collection must preserve the original control contract

Intervention data is useful only if its timing and action meaning match what the model is expected to learn. A slower teleoperator, a different control rate, or smaller rotational increments can teach a policy to move timidly even when every label is technically valid.

Compare expert and training distributions for per-step joint change, velocity, gripper range, command cadence, and observation age. This generalizes beyond any one yaw-speed incident: the problem is distribution shift in the corrective action stream.

Record lineage, then derive the training view

Keep the raw episode immutable and label, at every step, the model proposal, expert proposal, selected source, executed action, control mode, and takeover event. Training can later select expert-only windows or a mixture without destroying context.

Common recording failure

Raw RGB frames stored directly in columnar files can make a modest collection enormous. Store numeric state, action, labels, and frame indexes in Parquet; encode camera streams as video and preserve timestamp mapping.

A new checkpoint should require a descriptor, not a launcher branch

A deployment descriptor sits between the model bundle and the launcher. It does not contain the model or execute inference. It tells the system which verified bundle, contract, server, graph, camera profile, task catalog, and qualification procedure belong together.

schema: deployment/v1
name: example-policy

bundle:
  path: models/<family>/<version>
  required: [checkpoint, contract.json]
  verifier: verify_bundle.py

policy:
  frequency_hz: 30
  action_horizon: 32
  execute_prefix: 16

observation:
  camera_profile: camera-1280x720-30.yml

runtime:
  server: managed
  graph: dual-arm-policy.yml

qualification:
  tests: [contract, adapter, service, no_write_launch]

For an already-supported backend, onboarding becomes data entry plus evidence rather than another if model == ... branch. The same descriptor drives intake, qualification, launch, and rollback.

Keep package identity and local intake evidence separate

  • Publisher manifest: the file list, sizes, and hashes shipped with the bundle.
  • Local manifest: the downloader’s structured receipt containing object paths, sizes, source metadata, and computed hashes.
  • Local hashes: freshly computed content fingerprints, often also written as a flat SHA256SUMS file.

Cross-check all three. A complete download can still be the wrong checkpoint, and a correctly named checkpoint can still have one corrupted file.

Follow the first broken boundary

Do not start from the final visual symptom. Trace one observation and one action through the system and find the first point where the value stops satisfying its contract.

  1. What exact observation did the model receive?
  2. What raw action chunk did it return?
  3. What did timing and motion processing produce?
  4. What did the router and final safety boundary accept?
  5. What did the hardware receive and report back?

Most deployment arguments happen because someone jumps from question one directly to question five.

The recurring answer

When the system becomes mysterious, return to the dataset and training transforms. They usually resolve camera roles, units, action scale, cadence, start pose, and task language faster than another runtime workaround.

Keep the guide alive

This document should change when the architecture changes. Record the reason, the measured failure, the new contract, and the evidence that the fix works. A field guide is useful only while the next engineer can trust it.
