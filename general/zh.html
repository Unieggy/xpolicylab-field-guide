构建可靠的真机部署基础设施

通用现场指南
2026 年 9 月

如果你正在读这篇东西，大概率说明有人把“模型能跑”和几公斤硬件真的开始运动之间那一层交给你了。祝你好运。这部分通常不怎么光鲜，偶尔有点吓人，而且很多基础设施 bug 在日志证明真相之前，看起来都很像模型坏了。

这篇指南只保留能跨模型、跨机器人复用的工程方法：恢复训练合同，先建立不加技巧的基线，测量时序，只加入能解释的动作处理，并保留足够的数据 lineage，让每一条实际执行的动作都能被追溯。

如果你对时序、动作语义、录制格式、安全所有权或机器人接入做了重大修改，请在同一次变更里更新这篇指南。下一个工程师应该继承你的推理过程，而不是翻 terminal history 做系统考古。

数据集也是运行时规格的一部分

模型能返回有限值 tensor，并不能证明多少事情。两个 policy 都可能接收三张图像和一组状态，却对相机角色、RGB/BGR、字段顺序、单位、prompt 写法、时间戳，以及动作是绝对值还是增量有完全不同的理解。

把这些假设写成可执行的 contract。至少需要声明 observation key、shape、单位、相机角色、控制频率、action horizon、动作语义、任务词表和 normalization 资产。

工作原则

当文档、runtime 默认值和录制数据互相矛盾时，先检查数据和准确的训练 transform，再决定是否修改机器人 runtime。

先让不加技巧的原始策略真正动起来

先证明最短路径：新鲜 observation 进入 adapter，服务返回有限动作，动作语义正确，并且一条受监督命令到达预期 actuator。会抖但方向正确，是有价值的基线；非常平滑地驱动错误关节，不是。

不要一开始就加入 RTC、filter、spline、自动重试或放宽限制。每多一个机制，证据就多一层变化。只有理解原始 policy path 之后，才逐项加入。

  1. 验证相机身份、颜色、方向、分辨率和频率。
  2. 通过真实物理运动验证 state 顺序和单位。
  3. 验证 action 顺序、单位以及 absolute/delta 语义。
  4. 测量原始动作幅度和推理延迟。
  5. 执行一次有人监督、范围受限的硬件 canary。

把策略计算和硬件所有权分开

模型服务可以被替换、重启，甚至移动到另一台机器；硬件 writer 不应该随之变化。模型动作和专家动作都只是候选值，router 选择其一，最终安全边界负责验证，最后只能由一个 owner 下发命令。

异步推理必须处理已经过去的动作

推理和控制运行在不同的时钟上。请求在途期间，机器人仍会继续消费当前队列中的动作。新回复到达时，它最前面的几行其实描述的是已经过去的时刻。

通用处理方式很简单：在队列耗尽之前发起请求，测量期间经过了多少个 control step，从新回复中丢掉同样数量的行，只安装仍属于未来的部分。接缝处可以选择做一个很短的 blend；时间对齐不能省略。

触发时机应来自用 control step 表示的实测延迟，并保留少量 margin。模型、计算设备、图像链路、compiler 或网络变化之后，都需要重新测量。

不要混在一起

异步推理解决控制阻塞；alignment 删除执行时刻已经过去的动作；seam blend 减小两段有效未来动作之间的不连续。它们是三个不同问题。

根据实测问题选择动作处理

“让它更平滑”不是诊断。加入 processor 之前，先把原始逐步关节变化和 chunk 接缝跳变与训练数据比较。

观察到的问题适合的工具主要风险
只有新 chunk 到达时发生跳变先做 RTC alignment，再做短 seam blendblend 太长会让每次 replan 都变迟钝。
一个有效 chunk 内部存在高频噪声因果 low-pass filter过滤过强会增加延迟，也可能无法按时到达目标。
固定执行时间内只有稀疏 waypointSpline 或带时间参数的插值插值可能 overshoot，不适合频繁重新规划的命令。
单步或速度在物理上不可实现带 telemetry 的明确 rate/velocity limit长期频繁 clipping 会掩盖 contract 或 policy 问题。

Low-pass filter 通常需要跨 chunk 保留状态，并作用于 router 已选择的模型流、最终 dispatch 之前。除非过滤本身属于采集合同，否则不要过滤专家接管动作。

初始位姿属于数据分布

对人来说对称、方便的位姿，对 policy 可能是 OOD。应该从成功训练 episode 中采样 initial state；必要时先聚类，再选择有代表性且物理可达的状态。

记录选中状态、来源 episode、单位和容差。如果机器人无法安全到达它，应修复采集或 transition 流程，而不是凭感觉重新设计一个起始位姿。

覆盖范围限制

代表性采样只能从已有覆盖里选择，无法创造 demonstration 从未包含过的起始状态。

DAgger 采集必须保留原始控制合同

只有 intervention 数据的时序和动作语义与模型需要学习的东西一致，纠正数据才有用。更慢的操作员、不同的 control rate，或者更小的旋转增量，都可能训练出动作犹豫的 policy——即使每个标签在格式上都是合法的。

把 expert 和原训练数据的逐步关节变化、速度、夹爪范围、命令频率和 observation age 分布放在一起比较。这就是某一次 yaw-speed 问题背后的通用结论：纠正动作流发生了 distribution shift。

先完整记录 lineage，再派生训练视图

保持原始 episode 不可变，并在每一步记录 model proposal、expert proposal、selected source、executed action、control mode 和 takeover event。之后可以稳定地派生 expert-only window 或混合训练视图，同时保留上下文。

常见录制错误

把原始 RGB frame 直接写进 columnar 文件，会让不大的采集变得异常巨大。数值状态、动作、标签和 frame index 存 Parquet；相机流编码成 video，并保留时间戳映射。

新 checkpoint 应该只需要 descriptor，而不是新的 launcher 分支

Deployment descriptor 位于模型 bundle 和 launcher 之间。它不包含模型，也不执行推理；它告诉系统哪一个已验证 bundle、contract、server、graph、camera profile、task catalog 和 qualification 流程应该绑定在一起。

schema: deployment/v1
name: example-policy

bundle:
  path: models/<family>/<version>
  required: [checkpoint, contract.json]
  verifier: verify_bundle.py

policy:
  frequency_hz: 30
  action_horizon: 32
  execute_prefix: 16

observation:
  camera_profile: camera-1280x720-30.yml

runtime:
  server: managed
  graph: dual-arm-policy.yml

qualification:
  tests: [contract, adapter, service, no_write_launch]

对于已有 backend 能支持的 checkpoint，接入过程就变成填写配置并产出证据，而不是再增加一个 if model == ... 分支。同一份 descriptor 驱动 intake、qualification、launch 和 rollback。

把发布包身份和本地 intake 证据分开

  • Publisher manifest：随 bundle 发布的文件路径、大小和 hash 清单。
  • Local manifest：下载器生成的结构化收据，包含对象路径、大小、来源 metadata 和本地计算 hash。
  • Local hash：针对本地实际内容重新计算的指纹，通常也写成扁平的 SHA256SUMS。

三者需要互相核对。下载完整的文件仍可能是错误 checkpoint，而名字正确的 checkpoint 也可能有一个文件已经损坏。

沿着第一处断裂的边界排查

不要从最终视觉症状开始调参。让一条 observation 和一条 action 穿过整个系统，找出数值第一次不再满足合同的位置。

  1. 模型实际收到了什么 observation？
  2. 模型返回了什么原始 action chunk？
  3. 时序和动作处理生成了什么？
  4. Router 和最终安全边界接受了什么？
  5. 硬件实际收到了什么，又回报了什么？

大部分部署争论，都是因为有人从第一个问题直接跳到了第五个。

反复出现的答案

系统开始变得玄学时，回到数据集和训练 transform。相机角色、单位、动作幅度、频率、初始位姿和任务语言，通常都能在那里得到比 runtime workaround 更可靠的答案。

让这篇指南保持可用

架构改变时，文档也应该改变。记录修改原因、测量到的失败、新 contract，以及证明修复有效的证据。只有下一个工程师仍然敢相信它时，field guide 才有价值。
