真机部署基础设施：一份实用指南

Michael Lai
2026 年 9 月

如果你在读这篇东西，大概率说明机器人技术栈里最难画进架构图、偶尔也最吓人的那一段已经交到你手上了：从 checkpoint 到真正会动的硬件之间的所有环节。恭喜，也祝你好运。实际出的故障通常比架构图上画的更小、更怪，也更让人恼火。

一个 checkpoint 可以正常加载、返回有限值动作，放到真机上却几乎没法用。在我们的部署里，失败很少是“模型没加载出来”。更常见的是一处很小的错位：某个相机角色、某个单位、某个时序假设、某个初始位姿，或者某个 recorder 标签。

在 GR3、双臂 PiPER X 和 Astribot S1 上跨两个月折腾下来，同一个模式反复出现：runtime 在猜那些训练数据早就定死的细节。这篇指南记录的是最终沉淀下来的工作流程——先把原始策略跑通，调 RTC 之前先量时序，针对具体动作伪影选择运动处理，再让 DAgger 采集复现最初的训练契约。

如果你改了 runtime 的关键部分——机器人接入、时序语义、recorder 结构或安全链路——请在同一个 PR 里更新这篇指南。让未来的你，或者下一个接手的人，直接继承证据，而不是靠翻终端记录重新拼出整个系统。

01 · RUNTIME CONTRACT

张量形状对得上，不等于运行时契约成立

checkpoint 可以正常加载，吃进一份合成观测，吐出一个有限的 [32,14] 张量，然后仍然和这台机器人不兼容。形状校验只能证明内存布局没错。它证明不了含义没错。

两个形状完全相同的张量，可能编码着不同的相机角色、字段顺序、单位、时间戳或动作语义。这类错配经常能穿过所有离线断言，直到上了硬件才表现为动作软弱、乱抖或者不安全。

“三路 RGB 相机加 14 维状态，输出 14 维动作”只是接口摘要，不是部署契约。真正可执行的契约必须回答下面这些问题：

  • 哪一路相机是左？机器人的左，还是操作员监控墙上的左？
  • RGB 还是 BGR，谁来转——驱动、graph，还是 adapter？
  • 夹爪单位是米、毫米，还是行程百分比？
  • 动作块的第 0 行表示“此刻”，还是“下一个控制 tick”？
  • 它训练时看到的到底是哪几条 prompt？不是“关笔记本”，而是 "Close the laptop."——大写 C，带句号。

只要有一个答案缺失，这个 checkpoint 就没到能上机器人做资格验证的程度。

让 checkpoint 自己声明契约

每个可部署的模型包都带一份冻结的、机器可读的 contract.json，运行时负责强制执行。下面这份为了可读性删掉了一些行：

model-store/models/<policy>/<deployment>/<checkpoint>/contract.json 
{
  "observation": {
    "head_rgb":        "uint8[H,W,3] RGB",
    "left_wrist_rgb":  "uint8[H,W,3] RGB",
    "right_wrist_rgb": "uint8[H,W,3] RGB",
    "state":           "float32[14] absolute joints/grippers",
    "prompt":          "one canonical atomic-task instruction"
  },
  "action": {
    "representation": "absolute joint/gripper targets after output transform",
    "units":          "joint radians; gripper width in metres",
    "shape":          [32, 14],
    "control_hz":     30,
    "execute_chunk":  16
  },
  "canonical_prompts": [ "Close the laptop.", "Pick up one pen and place it in the pen holder.", ... ],

  "evidence_scope": {
    "establishes":        ["bundle restore", "finite synthetic inference", "I/O contract"],
    "does_not_establish": ["simulator success", "real robot success", "task success rate"]
  }
}

evidence_scope 这一段很重要：模型包自己记下了这次资格验证能证明什么、还有什么没验证。权重加载成功、合成推理输出有限值，不代表它在真机上能完成任务。

字段顺序也是契约的一部分

双臂 PiPER 的状态里有两条 6 自由度手臂和两个夹爪，但排布不是“12 个手臂关节，后面跟 2 个夹爪”：

real_world/robots/piper_x_dual/mapping.py 
ACTION_NAMES = (
    left_joint1 … left_joint6,   left_gripper,     # indices 0-6
    right_joint1 … right_joint6, right_gripper,    # indices 7-13
)
units = ("rad",)*6 + ("m",) + ("rad",)*6 + ("m",)

夹爪是交错排的，在索引 6 和索引 13。按直觉布局去写，右臂每个关节都会整体错一格，一个以米为单位的数落进本应是弧度的槽里，机器人会做出一个你很久都忘不掉的动作。整个过程维度检查一直通过，因为形状仍然是 [14]。

所以我们的 schema 把 fields、units 和 semantics 作为三组并列元组来携带，而不是一个光秃秃的维度；也所以任何东西动起来之前，两端都要先比对 schema_id。15 Hz 的动作块也不可能被悄悄按 30 Hz 执行——频率单独检查，因为这个我们也栽过。

颜色转换只做一次

我们的采集 profile 发布 bgr8。模型包契约写的是 RGB。必须有人在你能指出的那个位置，恰好把通道换一次。转两次会互相抵消。一次都不转，模型看到的是一张完全合理、只是颜色不对的世界图像，然后它的行为会变得古怪——而没有任何断言能抓住这种错。

软件替代不了的一项物理检查

我们在 PiPER 单元上第一次标左右相机就是错的。两路流都健康，两个序列号都钉在 instance profile 里，两个角色都稳定。全绿。软件层面没有任何东西能把它和“正确”区分开。

最后是有个人站到其中一台相机前面挥了挥手，才发现。

现在验收流程里每台相机都要做一次遮挡核验，因为相机身份是一个物理断言，只有物理测试能证伪它。在 UI 里把标签换到画面“看起来对”为止，你会得到一个稳定说谎的系统——那比一个明显在说谎的系统更糟。

02 · BASELINE

先把裸策略跑起来

不要一上来就把异步预取、RTC 切换和低通滤波同时打开，然后才开始验收。这套配置会掩盖故障到底出在哪一层边界上。

先让裸策略能跑，再加可选的运动处理。一个有点抖但方向正确的策略，是能用的基线。一个被层层处理过却根本不动的策略，没法告诉你问题出在模型、调度器、滤波器、安全门还是硬件通路上。

本手册里，裸基线指这套具体配置：

  • ACTION_RTC_MODE=disabled——不启用预取，也不做融合。
  • --no-model-filter——模型关节上不加低通。
  • 执行前缀用部署描述文件的默认值：32 行预测中执行前 16 行。这是评审过的值，不是随手试出来的。
  • 先加 --no-write。在 shadow 模式下，任何动作都到不了 SDK。

永远不会被关掉的是：schema 校验、频率一致性、generation 栅栏、新鲜度检查，以及机器人自有的最终门——有且只有一个进程能调 SDK 写入端。这些不是可选处理，而是系统底线。

有个细节我们花了很久才真正吃透：RTC 关掉时，按已执行动作做时间对齐仍然在跑。它是强制的，不是 RTC 的功能。上一个 episode 迟到的动作块照样会被丢弃，返回结果照样会按它在途期间消费掉的动作数对齐。原因马上讲。

测量裸动作的动态范围

不是看“动作顺不顺”。我们算动作块里每一步的最大绝对关节变化，再把这个分布和原始训练 episode 里逐关节速度分位数做比较。

δ= maxj | at+1,j − at,j |
δ
策略在一个控制步里想移动多远
at,j
动作块第 t 行、关节 j 的指令目标
maxj
对全部 14 个字段取最大，单个坏关节藏不住
t
动作块内部的行索引，不是墙钟时间

这一个数就能把三种在机器人上感觉完全一样的故障分开。太小：模型太保守，或者它的纠正数据采得太慢（§6）。太大：安全层马上要把大部分限掉，机器人会显得发闷、跟不上。不连续：有接缝、单位错误，或者策略确实进了不稳定区域。

两个真实数字用来校准。GR3 上一个“感觉发钝”的 checkpoint，中位最大关节步长是 0.041 rad；大家都觉得正常的那个是 0.064 rad——小了 37%，推理延迟完全一样。另一次运行里，原始步长冲到 1.13–1.19 rad，撞上 0.10 rad/step 的限幅，单个动作块里最多裁掉 97 个值。

这两件事报到我们这儿都是“机器人变慢了”。成因相反，修法也相反。

03 · TIMING AND RTC

时序故障看起来往往像动作很差

“发闷”只是一个视觉症状。它可能意味着模型步长偏小、队列饿死、轨迹被反复替换、安全限幅、观测过期，或者真的推理变慢。每种原因对应的处理方式都不一样。

8 月 12 日 GR3 的 pick-doll 运行是个有用的例子。checkpoint 系列没换，但动作变得犹豫，在停顿和短促爆发之间来回切换。

最先怀疑的硬件和算力方向，和日志对不上：

  • 推理变慢了？73 ms。和那次手感很好的运行一样。
  • 工作站内存吃紧？还有 102 GiB 空闲内存。
  • GPU 过热？36 °C。
  • 电机过热？机器人计算机约 20 °C，控制器日志里没有任何过温、过流或电机故障条目。
  • 存储或缓存压力？清掉 7.6 GB 包缓存，没有变化。

工作站和机器人控制器都是健康的。故障出在调度和动作准入上。

实际观察到的原因

三件事叠在一起，按责任从大到小排。

第一：启动命令覆盖了 RTC_TRIGGER_STEPS=24，而通过资格验证的值是 22。在 30 行的对齐队列下，trigger 24 意味着只执行 6–8 行就重规划——大约 0.2–0.27 秒——其中 4 行还在做融合。也就是说，每个更新间隔大约三分之二的时间都处在过渡里。

第二：rollout 中途，checkpoint 提出了一个 0.623 rad 的右手食指接缝，而准入上限是 0.56 rad。这个动作块被拒了，队列随后连续四次没有拿到新的尾部。这段饥饿造成了操作员看到的“停—动—停”动作。

第三：被拒之后，原始模型步长冲到 1.13–1.19 rad。安全层把它们限到 0.10 rad/step，单个动作块最多限了 97 个值。大量限幅在人眼看来，就是标准的“阻尼过重、发闷”。

这些没有一个是硬件问题。要定位它们，运行时必须为每个被接受的动作块发布完整的时序证据：实测延迟、对齐偏移、队列深度，以及过渡前后的接缝大小。

经过时间对齐是强制项

30 Hz 下，一个控制步是 33.3 ms。模型可能预测 32 行（1.07 s），而部署端只把验证过的 16 行执行前缀（0.53 s）放进队列。RTC 操作的是这个有效执行队列，不是运行时已经删掉的行。实测 70–75 ms 的推理大约吃掉 2–3 个控制步。

所以如果推理阻塞控制环，机器人会在动作块之间停 2–3 个 tick，你能听出来。如果推理异步跑、但回复从第 0 行开始安装，你就会重放 2–3 个“时刻已经过去”的动作，机器人会先往后窜一下再往前走。异步推理解决第一个问题。时间对齐解决第二个，所以它不是可选项。

c= (enow−esubmit) ⏟队列已消费 + ⌈Δtobs·f109⌉ ⏟观测年龄
c
回复开头要扔掉多少行
enow
此刻的执行步计数器
esubmit
发出请求时的同一个计数器
Δtobs
从采图到提交请求之间的纳秒数
f
动作频率（Hz）——双臂 PiPER 上是 30
T
模型实际返回的行数

c < T 才接受，然后执行第 c…T−1 行。否则整个回复都过期了：立刻丢弃并重新请求，而不是等下一次自然触发。

而什么时候去要下一个动作块，来自实测延迟，不是来自某个人看着顺眼的数：

ntrigger= min(E−1, q0.95+m + (p+τ)⏟ 仅融合 )
ntrigger
队列剩到这个深度就发下一次请求
E
模型输出截断后的有效执行前缀
q0.95
最近 32 次回复的实测往返延迟 95 分位
m
设计余量——默认 1 步
p
preserve 步数——我们选的，不是测出来的
τ
transition 步数——只在融合模式下计入

q 是测出来的；p 和 τ 是策略选择。preserve = 2 不代表 GPU 花了两步。它代表运行时在替换到达之后，故意保留两行对齐过的旧队列目标。当前 PiPER 操作员界面把 preserve 固定为 0，只暴露 transition 长度；共享运行时仍把 preserve 作为高级运行时契约字段。

Execution prefix允许执行的行32 行的模型输出可以在调度前截断为 16 行队列。
Auto latency何时请求用实测延迟分位数加余量；融合模式还要预留 transition 行。
No blend对齐后替换预取保持开启。过期的替换行被丢弃，但旧目标和新目标不做平均。
Preserve保留旧行回复到达并完成时间对齐后，故意保留这么多仍然有效的旧目标。
Transition融合后续行用选定的权重曲线混合接下来对齐过的旧目标和新目标。

下面是完整的一个周期。拖滑块——有意思的地方是看哪些行换了主人。

RTC 术语

客户端 RTC 对已经返回的动作块做经过时间对齐，并可选地融合接缝。就这些。previous-action 条件、冻结扩散步和梯度引导是模型后端的能力，打开预取并不会自动获得这些能力。

它们也可以被训练进去；我们 store 里就有一个模型包直接叫 …-trainrtc-d0to6-v1。那是那份权重的性质，和 real_world/rtc.py 做的事仍然是第三件独立的事。我们见过这三样在同一场对话里都被叫做“RTC”。

04 · MOTION CONDITIONING

平滑不是一种单一操作

平滑不是单一操作。动作块过渡、低通滤波、样条插值和速率限制，各自对应不同的失效模式，也各自位于控制链路的不同位置。

我们拿它跟上一代 DAgger-GR3 做了对比，所有人都同意后者感觉更顺。它做的平滑更少，少很多。它会完整执行一整个连贯的动作块——大约 1–1.7 秒的同一份计划——然后才去请求下一个。而且它允许每个在线关节步 0.15 rad，我们这套只允许 0.10。

所以更新的这套，滤波更多、限制更紧，看起来反而更差。

一套更频繁替换轨迹、又把自己追赶动作裁掉的系统，会比一套认准一份连贯计划的系统看起来更不平滑。每一次重规划都引入一条新边界；每一次裁剪都增加跟踪滞后。

我们当时建议的修法不是“放松安全上限”，而是 RTC_TRIGGER_STEPS=16——让相邻两次被接受的计划之间执行约 14 行连贯动作，而不是 6 行——所有限制原封不动。

通过资格验证的运行时里实际启用的处理器

在通过资格验证的配置里，真正开着的运动处理机制只有三个：

  • 模型关节上的一阶低通。双臂 PiPER 默认开启，α = 0.6。
  • RTC 时间对齐，以及可选的有界接缝融合。GR3 和 Astribot 用对齐；融合需要显式打开。
  • 五次多项式 minimum-jerk 分段轨迹，用于 Prepare、Home 和数据集位姿过渡。

PCHIP 重采样和动作块 QP 在 real_world/output.py 里都有实现。两个都默认关闭，GR3 提交的默认值就是 GR3_CHUNK_SMOOTHING=off，我们从来没有把其中任何一个验证到硬件上。这里提到它们，只是为了避免读代码时误以为它们已经启用。

低通行为与滤波器状态

yt= yt−1 +α ( xt− yt−1 ) , 0<α≤1
yt
本 tick 真正下发的滤波后目标
yt−1
滤波器自己上一次的输出——这就是状态
xt
本 tick 传进来的协调后目标
α
双臂 PiPER 上是 0.6。越小越平滑，也越滞后

这个滤波器是有状态的，而这个状态就是全部故事。如果目标停在 1.0、输出读数是 0.5，那不是“目标被削小了”——后续更新会继续收敛到 1.0。理论上没问题。但在有限长的动作块上，重规划通常在收敛之前就到了，所以真实行为更接近“永远只走到 60%”。这不是任何人想要的。

四个接线细节，每一个都是我们弄坏之后学到的：

  • 它在 RTC 协调之后跑，只作用于模型关节。
  • 在 Start、接管、HOLD、反馈失败或 generation 变化之后的第一步，它用新鲜的实测关节重新初始化。
  • 普通的动作块替换不会重置它。在那里重置，等于把这个滤波器本来要抹平的接缝又放回去。
  • 专家动作和两个夹爪宽度完全绕过它。夹爪上的相位滞后会错过抓取时机，没有任何 α 能修好这件事。

未滤波的目标先过一次检查，滤波后的目标在硬件控制进程写 SDK 之前再过一次最终安全门。滤波不是绕过那道门的方式。

固定时长的路点轨迹

五次轨迹处理的问题和低通不同。它在两个固定端点之间生成一段时间参数化运动，并明确约束起点和终点的速度、加速度。在当前运行时里，它只用于 Prepare、Home 和从数据集采样的起始位姿过渡，不进入持续重规划的模型动作流。

同一条多项式，不是同一种操作

路点轨迹用 s(u) 在两个固定端点之间生成运动；RTC 接缝融合可以复用这条曲线作为权重，在两份已经完成时间对齐的计划之间过渡；低通滤波则是递归计算，并不承诺何时抵达目标。尤其不要在每次模型重规划时重启一段五次曲线：端点持续变化，名义上的平滑最终会变成跟踪滞后。

05 · INITIAL STATE

初始位姿属于数据分布

几何上整齐的位姿，不一定是策略能用的起始状态。在 GR3 上，正运动学显示左手比右手前伸约 24 mm，左手食指尖高约 8 mm，于是团队做了一个更对称的初始化。

初始化 profile 从 …start-v5-claude-elbows 换成了 …start-v6-bilateral-fk，把双臂对称化，若干关节最多移动 0.084 rad（4.8°）。

几何变好了。行为变差了。

原因在数据集里一眼就能看到：v6 是一个算出来的双臂 FK 位姿，不是训练 episode 里的任何一帧。于是 checkpoint 第一帧观测就拿到一个分布外的轮廓。它表现成犹豫，一开始看起来像时间对齐问题。

逐关节取中位数有同样的缺陷。每个关节值单看都可能很典型，但组合起来的身体构型在零个 episode 里出现过。要选完整的已记录状态，不要用边缘统计拼出来的合成组合。

从已记录的起始帧里选完整位姿

PiPER 运行时改选完整的已记录帧：每条 prompt 十二个 follower-state medoid，取自训练候选 episode。每个候选必须满足：

  • 锚定在检测到的持续关节运动起始之前 8 帧（30 Hz 下约 267 ms）——示范者即将发力的前一刻。
  • 严格落在 episode 的前 22% 内。绝不取中段，绝不取尾部。
  • 后面至少还有 120 帧且存在显著的后续运动，保证它是真正的开始，不是一次停顿。
  • 远离任何终止状态。终止帧和完成后的帧被 schema 直接禁止。
  • 库里没有对应条目的 prompt fail closed，不退化成某个通用 home 位姿。

运行时，唯一的硬件控制进程只接受来自 SHA-256 绑定库的 pose id，然后独立重新推导关节限位和最大位移，之后才会执行任何动作。UI 从不发裸的 12 维目标。如果当前位置无法直达候选，硬件控制进程会经由声明的 clear/home 位姿拆成两段有界轨迹，每段下发前检查插值法兰高度——如果这条有界路径仍然不安全，它 fail closed，而不是去开某个门。

当前限制

现有示范几乎都共享同一个起始区域。这些 medoid 是有效的早期 episode 变体，不能证明起始分布有多样性。真正的覆盖需要从不同起始位置采集示范。

06 · DAGGER / HITL DATA

为什么 DAgger 数据也可能让策略变差

DAgger 数据只有在观测、动作、时间语义和标注语义都与将要消费它的策略一致时才有用。一次成功的专家接管，在这些契约漂移之后，照样能产出有害的训练数据。

早期的 GR3 recorder 里，六个互相独立的问题叠加在一起，把微调效果越搞越差：

这些故障属于旧版 GR3 recorder，现在已经修掉了。它们的失效模式仍然值得记下来，因为六个里有四个，不做显式的数据审计就根本看不见。

  1. 后续的纠正被悄悄丢掉。recorder 在每次 save 或 discard 之后清空自己的 episode_index，没有 index 就拒绝开始录——但控制器只在模型 episode 开始时发一次 index。所以一个 episode 里第一次接管录得好好的，第二次没有。我们的数据集被系统性地偏向“第一次纠正”，而那通常是最没意思的一次。
  2. label.valid 被污染。重复的接管状态消息会发出一个 label_valid=false 的默认决策。原始采集里：88,825 个 false 对 77,354 个 true，约 20% 的对齐专家动作，最近的 validity 样本是 false。我们的严格转换器没有天真地消费那条流，所以模型包幸免了——但任何按最近时间戳 join 的东西都会把这个错误整个继承下来。
  3. “成功”只表示操作员按了 save。不表示玩偶最后落在了任何特定的地方。
  4. 我们只录了接管片段。没有紧邻其前的模型失败，也没有其后完成的恢复。孤立的纠正，任务上下文被切掉了。
  5. 数据配比严重过采样了纠正。新 DAgger 数据占每个 batch 64 中的 28——43.75%——到 step 4000 时每个片段大约被看了 8.3 次。短促而显眼的纠正动作，会盖掉父模型原本已经具备的长程成功行为。
  6. 六段录制里，安全限幅过的动作配着未裁剪的标签。在严格重建里被隔离了。

给个量级：严格数据集最后是 22,996 帧 / 13,448 条有效 H32 query。后来的混合模型包报告 211 个 DAgger 片段、22,742 帧、16,201 条有效 query，配比大约 40% DAgger / 60% replay。

按控制 tick join 流

相机跑 30 Hz。硬件控制器跑 60、100 或 200。GR3 上我们测到机器人状态 ≈30.29 Hz，专家动作 ≈99.88 Hz，时间对齐通常在 5 ms 以内。这些是很漂亮的数字。它们仍然不足以支撑按最近时间戳 join，因为“最近”可能悄悄跨过一个接管边界，或者取到错误的 validity 心跳。

所以身份改成因果分配：唯一的硬件控制进程只在 SDK 下发成功之后才分配 control_tick_id。这次下发对应的已执行动作、被选来源、标签有效性和被接受的证据，共享同一个 id。Router 侧的提议 id 单独保留为 decision_control_tick_id，并且被明确规定不作为硬件动过的证据。任何缺失、冲突，或者只能靠时间戳回退才能 join 的区间，一律进隔离区——绝不猜成有效标签。

这就带出另一件值得分清楚的事。这条流水线里有五个不同的张量，大家都管它们叫“动作”：

一行可训练，当且仅当 source = EXPERT、接管参考有效、安全有效，并且 label.valid = true。标签本身是 action.expert_aligned_unclipped_robot——操作员对齐之后的意图目标。

未裁剪的意图是更干净的标签，但前提是机器人执行的基本就是那个目标。如果安全层实质性地改动了它，用意图训练就等于教出一个从未在环境里被示范过的行为。那些录制被隔离而不是修复，因为被污染的意图标签没法被可靠地反推回来。

显式对齐接管过渡

在接管的上升沿，我们恰好一次地固定两个构型——机器人的实测构型和专家设备的构型。之后的一切都是相对的：

aexpert(t)= q0robot + ( qexo(t) − q0exo )
aexpert(t)
对齐后的专家目标，也就是训练标签
q0robot
接管上升沿那一刻机器人的实测构型

外骨骼当前的构型

没有它，你一接管，机器人就会朝外骨骼那个毫不相干的绝对构型跳过去。有了它，转移过来的是操作员的运动——那本来就是你想录的东西。

专家速度变成了数据集属性

QNexo adapter 的默认值是 EXO_WAIST_YAW_SPEED = 0.1，adapter 里再除以 100，得到每次更新 0.001 rad——在设计的 100 Hz 环路下大约 0.1 rad/s。产出的专家纠正肉眼可见地慢。

凭手感把它提到 0.5，遥操作体验好很多，同时也改变了下一个 checkpoint 将要学习的纠正分布。因为模型预测的是未来目标位置而不是速度，更慢的标签意味着在 32 步预测窗口内目标变化更小。当同样的视觉和状态同时对应较快的预训练标签与较慢的 DAgger 标签时，损失函数会把二者平均成幅度偏小、反应迟疑的动作。

正确的标定做法是从原始 episode 里算逐关节的速度和加速度分位数，然后去匹配它们。另外：不要试图靠给 yaw 值乘一个系数来修复旧的慢数据。那会破坏时间上以及手臂／腰部之间的协调，产出的标签单看都合理、合起来不可能。

把相机流按视频编码

数值、事件和时间对齐元数据属于 Parquet。相机帧不属于，而且这个账算得根本不接近。一个真实的 30 Hz 双臂 PiPER episode，三路 1280×720 RGB 以 Parquet 数组存储：

相机流：4.59 GB。全部 14 条数值／事件／标签流加起来：0.59 MB。episode 时长：52.6 秒。

这正是你能预测出来的结果——3 × 1280 × 720 × 3 字节是每帧 2.76 MB，乘 30 Hz 是 82.9 MB/s，乘 52.6 秒是 4.36 GB。对带相机噪声的 uint8 数组，Parquet 压缩基本没有作用，所以图像最后大约是其他一切的 7,700 倍，而且没有任何压缩设置能改变这个比例。编码成 H.264 MP4，把帧 → 时间戳 → control_tick_id 的映射留在表格元数据里，因果关联就仍然成立。

07 · MODEL ONBOARDING

一个 checkpoint 该配一份部署描述文件，而不是一个新的 launcher 分支

部署要能重复执行，前提是每个跟 checkpoint 有关的问题都只有一个机器可读的事实来源。部署描述文件（descriptor）就坐在模型 bundle 和通用 launcher 之间：它位于 policy/<adapter>/deployments/，声明 bundle、时序契约、相机 profile、服务方式、任务目录和验证步骤，再由 launcher 读取并选择正式 graph。

我们最后收敛到的规矩是：一个新 checkpoint 需要的是一份部署描述文件，而不是 launcher 里的一个新分支。launcher 需要知道的关于某个模型的一切都是数据。launcher 本身里没有任何 if model == …。

policy/<adapter>/deployments/<deployment>.yml  ·  节选 
bundle:                          # identity and immutability
  default_path: model-store/models/<policy>/<deployment>/<checkpoint>
  required:     [checkpoint/model.safetensors, contract.json]
  verifier:     policy/<adapter>/verify_bundle.py

policy:                          # timing contract, mirrored from contract.json
  action_frequency_hz:   30
  action_horizon:        32
  default_execute_chunk: 16
  default_execute_mode:  auto    # follow the model's execute_prefix_steps

observation:
  camera_profile: camera_profiles/piper-x-dual-rgb-1280x720-30.yml

server:
  default_mode: managed          # launcher owns the PolicyServer lifecycle

tasks:
  catalog_path: contract.json    # authority is the bundle, not this file

intake:
  provider:       aliyun_oss
  expected_bytes: FROM_PUBLISHER_MANIFEST

qualification:
  verifier_args: [--full-manifest]
  tests:         [ tests/test_inference.py, …, tests/test_robot_contract.py ]

从上往下读一遍，你就能回答：哪份权重、怎么校验、什么频率、用哪些相机、怎么服务、走哪张 graph、用哪些 prompt、从哪来、由哪些测试证明。这就是全部意图。

两条命令覆盖整个生命周期——onboard 负责首次接入，qualify 负责已安装的运行时。同一套分阶段流程会校验每个文件、准备隔离的模型运行时、执行 descriptor 声明的测试、绑定一个空闲的 loopback 端口、启动由 launcher 管理的 server、用符合契约的合成观测探测服务，再做一次禁写的 launcher dry run。产出是一份 JSON 报告和逐阶段编号日志。

这里的三重校验各管一层：本地哈希是当前文件实际算出的 SHA-256；本地 manifest 是接入后生成的完整文件清单；发布方 manifest 是上游随 bundle 交付的权威清单。三者一致，才能证明下载没有缺文件、本地没有被改写，而且安装内容确实对应发布者声明的那一份。

端口归属

因为看到 address already in use 时，最诱人的做法是把占着端口的东西全杀掉，而我们见过这么干的下场。正确做法是找出监听者并校验它的 WebSocket HELLO：部署身份一致就显式复用；不一致就只停 launcher 自己拥有的那个进程。

一个来自别的 checkpoint、恰好在对的端口上应答的野生 server，会自信地给你喂一整个下午的错误动作，而你的日志里不会有任何一行看起来可疑。

核心的归属不变量很严格：有且只有一个进程可以调 SDK。模型动作和专家动作都只是提议。router 选来源，机器人自有的门放行或 HOLD，硬件控制进程写入，recorder 旁观一切、而且永远没有硬件权限。

VLM 站在这一切之上，而这个位置是刻意的。任务选择和恢复推理是慢速、会出错的；运动控制是硬实时的。把它们直接接在一起，一次两秒的语言模型往返就会跑进一个 33 毫秒的控制环里。

supervisor 不是第二张 Dora 控制 graph。它通过带认证的 loopback API 通信，只能发出 checkpoint 声明目录里的 prompt，而且从不发关节目标。唯一写者按实际收到的模型动作计算它的 rollout 预算。执行一旦开始，实时路径里没有 VLM。

08 · FAULT ISOLATION

沿着第一处断裂的边界排查

从第一个失效的边界开始查，不要从机器人最后表现出来的视觉症状倒推。下面这张表按现场排查顺序列出回报最高的检查项。

症状我们很想做的事通常真正的原因
机器人完全不动怪推理，加平滑ENABLE_WRITE=0——这比想象中常见。然后才是生命周期状态、控制器模式、新鲜的 SDK 反馈、实际下发计数。
反馈报 0 Hz调低新鲜度阈值CAN 身份、供电、控制器模式。放宽的看门狗造不出缺失的反馈——它只是让你去指挥一台你看不见的机器人。
能加载但行为随机以为形状对上了就是兼容归一化统计量、tokenizer、相机键、状态字段顺序、单位、动作逆变换。对着模型包比，别对着记忆比。
左右反了把 UI 标签换到看起来对为止顺着序列号 → instance 角色 → graph 输出 → 观测键 → 训练相机角色追一遍。然后去相机前挥手。
相机启动后卡死把期望的 USB 3.2 放宽到 2.1带宽、hub、线缆。帧号缺口才是测量值；放宽身份校验造不出帧。
停—动—停把接缝融合加长队列饥饿、被拒的替换、迟到的结果。加长融合只会更糟。见 §3。
动作过激把所有平滑器一次全加上把原始逐步速度和训练分位数比较，然后只加一个能归因的处理器。
数据集巨大调高 Parquet 压缩数值走 Parquet，相机走 MP4。比例约 7,700:1，压缩设置只是噪声。

这些背后的做法是同一个：不要从最终的视觉症状开始调。跟着一条观测和一个动作穿过整个系统，找到数值第一次不再符合运行时契约的那个边界。五个问题，按顺序——模型收到了什么，它返回了什么，运行时调度了什么，硬件控制进程接受了什么，物理上发生了什么。大多数争论的发生，是因为有人从第一个问题直接跳到了第五个。

五组最容易混淆、也最耗排查时间的概念

这里每一组，一旦在某个人脑子里或某份文档里塌缩掉，都会产出一类特别难找的 bug——因为所有相关的人用的是同一个词。

  • 当前 vs 历史。当前代码才是事实来源。八月的一段聊天记录，是关于一个此后可能已经变了的系统的案例。§6 里的 recorder bug 是真的，也已经修了；能迁移的是那些失败的形状。
  • 客户端 RTC vs 模型原生引导。上面说过了。打开预取，不会凭空增加模型条件或生成时引导。
  • 原始 vs 协调后 vs 已执行。三个不同的张量。一旦开了接缝融合，协调后的流就不再逐字节等于原始回复，而在证据链路里把它标成"raw"，会污染它下游的一切。
  • 原始 episode vs 派生视图。完整录制保留上下文；训练视图是它的一个严格投影。两个都留着，不可变，这样一个标注决定可以被重新推导，而不是拿来吵架。
  • 资格验证 vs 移动授权。报告全绿证明的是 restore、契约形状、服务一致性和一次禁写 dry run。它对任务成功率什么都没说——模型包自己的 evidence_scope.does_not_establish 就明说了。让真机动起来，需要一次显式的 live-run 请求、写授权门，以及一个手放在急停上的人在场的监督 canary。

数据集优先的排查

一致的结果是操作层面的，不是什么新发现：当部署行为变得难以解释时，先回到数据集和训练契约，再考虑加运行时修正。

从数据里采起始位姿。从数据里测专家速度。从数据里恢复相机角色和时序。把动作语义追溯回那个生成数据的变换。

训练契约显然修不了一根断掉的 CAN 线，也修不了一台坏相机。它做的是：不让硬件故障被误判成模型故障，也不让一次分布外部署被运行时小技巧“修好”、然后悄悄毒化下一轮训练。

没解决的限制还在。示范数据里没有足够的起始位姿多样性，medoid 筛选造不出缺失的覆盖，40/60 的 DAgger 回放比例是经验值而不是推导出来的，单次 rollout 也分不清方差和系统性的策略缺陷。

09 · 硬件排障手册

GR3 和 PiPER 的故障方式完全不同

GR3 和双臂 PiPER 会在不同的物理边界上出问题。GR3 是承重人形机器人，首先要保持吊装支撑，并从控制器回读确认全身 PdStand；PiPER X 是固定底座，但失能的机械臂仍会在重力下坠落，所以设备身份、CAN 反馈和伺服使能状态排在第一位。

承重人形机器人 GR3 排障手册 ↓ 吊装支撑、脚底承重、PdStand，以及 Aurora 控制器状态链。 固定底座双臂机器人 双臂 PiPER X 排障手册 ↓ 两路 CAN 身份、每条手臂六个使能位、三路相机物理角色，以及重力安全恢复。
GR3

支撑和平衡就是安全边界。

进程正在运行，并不能证明 GR3 已经可以安全下放。吊装必须保持连接；先从控制器回读确认全身 PdStand，再让双脚承重。

01吊起完整支撑机器人，清空跌倒区域并整理线缆。
02PdStand从控制器回读确认全身 PdStand。
03下放小幅移动吊装，直到两只脚掌平放。
04承重检查确认双脚稳定承重，机器人响应稳定。
05启动 policy只初始化一次，等待准确的 READY 交接。

五项检查做完，再运行

  1. 先吊起。完整支撑机器人。清空脚边、线缆和跌倒区域，急停必须触手可及。
  2. 确认 PdStand。等待控制器准确回读全身 PdStand。仅仅看到 AuroraCore 进程在运行，并不能证明状态正确。
  3. 缓慢下放。用很小的吊装位移让两只脚掌平放。任何一只脚折叠、打滑或勾到线缆，立刻停。
  4. 感受承重。轻推骨盆向后，直到能感受到地面对机器人的向上反作用力。吊装仍保持随时承重，再轻推一次，确认双脚没有滑动，吊带也没有突然受力。
  5. 先初始化，再运行。只按一次 i。等待 UserController_A + RemoteState + Navigation、初始姿态完成和 CONTROLLER ready，再通过当前配置的任务/启动控制让模型开始下发。发生 fault 时不要连续点击初始化。
GR3 控制器状态链

AuroraCore → 全身 FSM 2: PdStand → 下放并让双脚承重 → i → 全身 FSM 3: UserController_A + 上半身 FSM 2: RemoteState + 速度源 Navigation → 初始姿态 → CONTROLLER ready
PdStand 是有吊装保护时的下放状态。按下 i 后，UserController_A 负责下半身 RL 平衡与行走，RemoteState 接收通过准入的上半身指令；readiness 还要求速度源为 Navigation。这里两个“FSM 2”属于不同的状态机；当前生产交接不是全身 FSM 11。AuroraClient 会请求并校验状态，也会发送通过准入的指令；真正的控制器仍是 AuroraCore。

GR3 问题处理方式
没有确认 PdStand保持机器人完全吊起，读取全身 controller/FSM 错误，不要继续下放。
脚已触地，但感受不到向上反作用力吊装还在承担重量，或者有一只脚没踩实。小幅继续下放，再检查两只脚掌。
脚底滑动，或吊带突然受力不要运行 policy。恢复完整吊装支撑，检查脚底位置、电机反馈和 PdStand 状态回读。
初始化失败让吊装保持随时承重，并核对准确的全身状态。不要假设机器人已经恢复到 PdStand；修复失败的交接阶段后再重试。
需要停止 GR3x 会阻止模型继续下发，并主动保持实测上半身姿态；Ctrl-C 会请求并等待 PdStand 确认，同时保持 AuroraCore 运行。不要把停止 AuroraCore 当作正常清理流程。
GR3 停止条件

整次运行结束之前，吊装不能拆。状态、支撑或平衡有任何不确定，就在启动 policy 之前停下来。

PiPER X × 2

身份和反馈就是安全边界。

每条手臂有自己的 SocketCAN 总线，每台相机有固定的物理角色。adapter 序列号、线缆标签、反馈数据和实际左右侧测试全部对得上，逻辑名称才可信。

机械臂撞到地面并失能时

  1. 先停 runtime。停掉 policy 并退出 Dora graph，确认 XPolicy 的 PiPER owner 已断开。维护 UI 绝不能和 runtime 同时存在，变成第二个 writer。
  2. 排除物理原因。急停保持触手可及，托住失能机械臂抵抗重力，清掉地面或障碍物接触，检查手臂、夹爪和线缆。机械臂还被卡住时不要 Enable。
  3. 打开现场批准的 PiPER 维护 UI。刷新 CAN，按稳定接口选受影响的那一侧；接口还没 UP 才以 1 Mbps 激活；选 instance profile 声明的固件，然后 Connect。
  4. 先读状态，再发命令。确认关节反馈和实际物理侧。点 Enable。如果还有锁存 fault 导致 Enable 被拒，继续托住手臂，按 UI 或厂商流程执行一次 Reset，再 Enable。解释不了的 fault 不要反复 Reset。
  5. 证明恢复。六个关节使能位必须全部为 enabled，反馈必须持续更新，follower arm 还必须回报 CAN-control/follower mode。不要拿 Go Zero、Move P/L 或轨迹回放当使能测试。
  6. 归还所有权。Disconnect 并关掉维护 UI。先跑仓库的 no-write 设备验证，再启动正式 launcher。XPolicy owner 必须重新成为唯一的 SDK writer。

cd <site-approved-piper-maintenance-ui>

维护警告

维护程序用的是官方 pyAgxArm SDK。Disable、Reset、角色切换、Go Zero 和轨迹控制都可能让机械臂运动或在重力下坠落。软件急停替代不了物理急停；只用恢复所必需的最少控制。

稳定 CAN 身份

Linux 枚举顺序在重启或重新插拔后可能变。USB-CAN 序列号标识 adapter，稳定 netdev 由它派生。SDK 可能不提供有用且唯一的机械臂序列号，所以 adapter 必须和对应侧的 CAN harness 物理绑定并贴好标签。工位 commissioning 时，用一次受控的单臂断开测试确认左右映射。

双臂 PiPER 问题处理方式
Device ... does not exist把配置的 USB-CAN 序列号解析成稳定 netdev。物理 harness 对应关系确认之前，不要改另一条接口的名字。
反馈 0 Hz，或机械臂反馈缺失查机械臂供电、物理急停、CAN 线缆、终端电阻、接口 UP 状态和 1 Mbps bitrate。绝不能降低 freshness 阈值来掩盖反馈缺失。
六个关节使能位一直是 false停掉 runtime，托住机械臂，在维护 UI 里查状态；只有确认了 fault 原因才清锁存错误，再 Enable，并验证反馈位，而不是只看命令返回值。
机械臂报 Standby，而不是 CAN control确认它确实是 follower/output arm，并且选对了总线。只有按 UI 要求把目标机械臂电气隔离后，才能执行 follower/CAN-mode 操作；较旧固件可能还要断电重启。
主动拔掉了一条机械臂缺失的逻辑角色必须和物理侧一致。拔掉物理右臂却报 left-arm error，任何 live run 之前都要先修 instance/harness 映射。
相机显示在 UI 的错误一侧别信 tile 的屏幕位置。用物理遮挡测试验证 serial-to-role 映射，再确认模型键映射。UI 标签和模型输入是两回事。
相机协商成 USB 2.1查线缆、hub、端口和总带宽，恢复 USB 3.x。把期望 profile 改成 2.1 只会压掉警告，挡不住后面的丢帧和超时。
相机短暂工作后超时查 frame number 是否持续增长和 USB 拓扑。减少带宽竞争或恢复训练时的相机 profile；不能把最后一帧反复发送然后管它叫 live。
双臂 PiPER 停止条件

任意一条机械臂失能、状态过期或身份不明确，就不要启动 policy。两条手臂的状态和所有必需相机角色都必须 fresh，模型的 14 维 observation 才有效。
