真机部署基础设施实战指南

如果你正在读这篇东西，大概率说明机器人系统里最不光鲜、偶尔也最吓人的那一段已经落到你手上了：把 checkpoint 和真正会动的硬件之间那一整条链路接起来。恭喜，也祝你好运。实际出问题的地方通常比架构图写得更小、更怪，也更烦。

过去几个月我们一直在把 Pi0.5 和 FastWAM 的 checkpoint 装到真硬件上——一台 GR3 人形、一套双臂 PiPER、一台 Astribot S1。几乎所有我们一开始的假设，最后都以某种具体又烦人的方式被证明是错的。下面这些是值得写下来的。

如果这些事情有一条共同的线索，那就是：数据集不只是训练输入，它是你手上关于运行时最可靠的一份规格书。README 可能是错的，训练那个 checkpoint 的人可能已经离职了。但数据集不会在这些事情上撒谎：模型看到了什么、顺序如何、单位是什么、频率多少、从什么起始位姿开始。

如果你改了 runtime 的关键部分——新机器人、时序语义、录制格式或安全链路——请在同一个 PR 里把这篇指南一起更新。别让未来的你，或者下一个倒霉的人，靠翻 terminal history 做系统考古。

01

形状是对的，机器人是废的

这是坑我们次数最多的一种失败。checkpoint 加载成功，restore 干净，你喂给它一份合成观测，它回你一个漂亮的 [32,14] 浮点数组，全是有限值。每一条断言都过了。然后你把它放到机器人上，它做出的动作介于"什么都没做"和"有点吓人"之间。

形状永远是对的。这某种意义上就是问题所在——形状本来就不是会出错的那一部分。两个张量可以形状完全一样，却描述两台完全不同的机器人。

"三路 RGB 相机加 14 维状态输出 14 维动作"不是合同，那是形状。真正决定这东西能不能跑的问题，全都在形状下面一层：

  • 哪一路是左？机器人的左，还是操作员监控画面里的左？
  • RGB 还是 BGR，谁负责转——驱动、graph，还是 adapter？
  • 夹爪的单位是米、毫米，还是行程百分比？
  • chunk 的第 0 行是"此刻"，还是"下一个控制 tick"？
  • 它见过的到底是哪几条 prompt？不是"关笔记本"，而是 "Close the laptop."——大写 C，带句号。

这些在形状检查里一个都看不见。而它们每一个都能毁掉你一个下午。

所以现在我们让 checkpoint 自己回答这些问题

我们部署的每个 bundle 都带一份冻结的、机器可读的 contract.json。不是文档——是运行时会去读、并且会强制执行的文件。下面是真实的一份，删了些行：

model-store/models/<policy-family>/<checkpoint>/contract.json 
{
  "observation": {
    "head_rgb":        "uint8[H,W,3] RGB",
    "left_wrist_rgb":  "uint8[H,W,3] RGB",
    "right_wrist_rgb": "uint8[H,W,3] RGB",
    "state":           "float32[14] absolute joints/grippers",
    "prompt":          "one canonical atomic-task instruction"
  },
  "action": {
    "representation": "absolute joint/gripper targets after output transform",
    "units":          "joint radians; gripper width in dataset units",
    "shape":          [32, 14],
    "control_hz":     30,
    "execute_chunk":  16
  },
  "canonical_prompts": [ "Close the laptop.", "Pick up one pen and place it in the pen holder.", ... ],

  "evidence_scope": {
    "establishes":        ["bundle restore", "finite synthetic inference", "I/O contract"],
    "does_not_establish": ["simulator success", "real robot success", "task success rate"]
  }
}

最后那一段是整个仓库里我最喜欢的东西。bundle 在自己内部声明了它不能证明什么。它挡下来的"过于乐观的周五傍晚"，比任何测试覆盖率都多。

那个 14 维向量的排布跟你想的不一样

不许看，快速回答：我们双臂 PiPER 的状态是 14 个数，两条 6 自由度手臂各带一个夹爪。它是怎么排的？

如果你说"12 个手臂关节，然后 2 个夹爪"——一样，大家都这么说。它是错的：

real_world/robots/piper_x_dual/mapping.py 
ACTION_NAMES = (
    left_joint1 … left_joint6,   left_gripper,     # 索引 0-6
    right_joint1 … right_joint6, right_gripper,    # 索引 7-13
)
units = ("rad",)*6 + ("m",) + ("rad",)*6 + ("m",)

夹爪是插在中间的，在索引 6 和索引 13。按直觉那种排法去写，右臂每个关节都会错位一格，一个米量级的数落进一个期待弧度的槽里，机器人会做出一个你会记很久的动作。而维度检查全程都是通过的，因为形状仍然是 [14]。

所以我们的 schema 带的是 fields、units 和 semantics 三个并列元组，而不是一个光秃秃的维度；也所以任何东西动起来之前，两端都要先比 schema_id。15 Hz 的 chunk 也不可能被悄悄按 30 Hz 执行——频率是单独检查的，因为这个我们也错过。

颜色是最阴的那个

我们的采集 profile 发布 bgr8，bundle 合同写的是 RGB。必须有人在一个你能指出来的地方，恰好转一次。转两次会互相抵消。一次都不转，模型看到的是一张完全合理、只是颜色不对的世界图像，然后它的行为会变怪——而任何断言都抓不到。

这个我们在软件里根本抓不到

我们在 PiPER 上第一次标的左右相机就是错的。两路都健康，两个序列号都钉在 instance profile 里，两个角色都稳定。全绿。软件层面没有任何东西能把它和"正确"区分开。

最后是有人站到其中一台相机前面挥手，才发现的。

现在验收流程里每台相机都要做一次遮挡核验，因为相机身份是一个物理断言，只有物理测试才能证伪它。在 UI 里把标签换到画面"看起来对"为止，你会得到一个稳定说谎的系统——那严格来说比一个明显在说谎的系统更糟。

02

我们总想跳过那个无聊的基线

每一次我们赶时间，都会一口气把整套东西全打开——异步预取、RTC 混合、低通滤波，全部——然后开始研究机器人为什么行为怪异。这从来没有一次让我们更快。

所以现在的规矩，而且我们相当虔诚地遵守：先让裸策略跑起来，再加别的。原始动作，正确合同，送到机器人。它会有点抖，没关系。一个会抖但动作合理的策略能告诉你巨量信息；一个被层层处理却从来不动的策略，几乎什么都告诉不了你。

"裸"是一份具体配置，不是一种感觉：

  • ACTION_RTC_MODE=disabled——不学预取点，不做混合。
  • --no-model-filter——模型关节上不加低通。
  • 执行前缀用 descriptor 默认值，32 步 horizon 里的 16 步。是评审过的值，不是一次实验。
  • 先 --no-write。影子模式，任何东西都不到 SDK。

而永远不会被关掉的是：schema 校验、频率一致、generation 栅栏、新鲜度检查，以及机器人自有的最终门加上有且只有一个进程能调 SDK writer。这些不是"处理"，这是地板。

有一个细节我们花了点时间才真正吃透：RTC 关掉的时候，已执行动作对齐仍然在跑。它是强制的，不是 RTC 的特性。上一个 episode 的迟到 chunk 照样会被丢弃，返回结果照样会按在途期间消费掉的动作数做对齐。为什么，马上说。

我们实际上看什么

不是"动作看着顺不顺"。我们算 chunk 里每一步的最大绝对关节变化，然后把它的分布和原始训练 episode 的逐关节速度分位数比较。

δ= maxj | at+1,j − at,j |
δ
策略在一个控制步里想移动多远
at,j
chunk 第 t 行、第 j 个关节的指令目标
maxj
对全部 14 个字段取最大，单个坏关节藏不住
t
chunk 内部的行索引，不是墙钟时间

这一个数就能把三种在机器人上感觉完全一样的失败区分开。太小：模型太保守，或者它的纠正数据采得很慢（见 §6）。太大：安全层马上要把大部分限掉，机器人会显得又闷又跟不上。不连续：接缝、单位错误，或者策略确实进了不稳定区域。

两个真实数字用来校准。GR3 上一个"感觉发钝"的 checkpoint，中位最大关节步长是 0.041 rad，而大家都喜欢的那个是 0.064 rad——小了 37%，推理延迟完全一样。另一次运行里，原始步长冲到 1.13–1.19 rad，撞上 0.10 rad/step 的限幅，单个 chunk 里最多裁掉 97 个值。

这两件事报到我们这儿都是"机器人变慢了"。成因相反，修法也相反。

03

"今天机器人怎么这么钝？"

这是我们手上最好的一个调试故事，因为所有凭直觉给出的答案都是错的，包括我自己的。

8 月 12 日，GR3，pick-doll 任务。checkpoint 跟前一天是同一系列，但机器人明显更差了——犹豫、停顿，那种一卡一卡的动法，会让房间里所有人立刻假设有什么东西过热了。

那些显而易见的假设，以及日志实际上说了什么：

  • 推理变慢了？73 ms。和那次感觉超好的运行一模一样。
  • 工作站在抖？内存还剩 102 GiB。
  • GPU 在烧？36 °C。
  • 电机过热？机器人计算机约 20 °C，控制器日志里没有任何过温、过流或电机故障条目。
  • 是不是哪个缓存满了？我们清掉了 7.6 GB 的包缓存。毫无变化，跟预期完全一致，但我们还是觉得有义务试一下。

所以机器是好的。问题是我们。

实际发生的事

三件事叠在一起，按责任从大到小。

一：启动命令覆盖了 RTC_TRIGGER_STEPS=24，而通过资格验证的值是 22。听起来像没差别。不是。在 30 行的对齐队列下，trigger 24 意味着只执行 6–8 行就重规划——大约 0.2–0.27 秒——而其中 4 行还在做混合。所以每个更新间隔大约三分之二的时间都待在过渡里。机器人一直在改主意，然后又把自己平均掉。

二：rollout 中途，checkpoint 提出了一个 0.623 rad 的右手食指接缝，而准入上限是 0.56 rad。这个 chunk 被拒绝了，拒得没错。但队列随后连续四个 chunk失去了尾部——真正的饥饿。这就是操作员感受到的"停—动—停"。

三：被拒之后，原始模型步长冲到 1.13–1.19 rad。安全层把它们限到 0.10 rad/step，单个 chunk 最多限了 97 个值。大量限幅在人眼看来，就是标准的"发闷、发钝"。

这里面没有一件是硬件问题，而且如果没有每个被接受的 chunk 都会发布的对齐证据——实测延迟、对齐偏移、队列深度、过渡前后的接缝大小——这些一件都查不出来。

为什么对齐这件事重要

算一点小学算术，整件事就明显了。30 Hz 下一个控制步是 33.3 ms。32 行 horizon 是 1.07 秒的计划。GR3 上实测的 Pi0.5 推理是 70–75 ms——就算 2–3 个控制步。

所以如果推理阻塞控制环，机器人会在两个 chunk 之间停 2–3 个 tick，你能听出来。如果推理是异步的、但回复从第 0 行开始安装，你就会重放 2–3 个"时刻已经过去"的动作，机器人会先往回窜一下再往前走。异步推理解决第一个问题。对齐解决第二个，所以它不是可选项。

c= (enow−esubmit) ⏟队列已消费 + ⌈Δtobs·f109⌉ ⏟观测已过期
c
回复开头要扔掉多少行
enow
此刻的执行步计数器
esubmit
发出请求时的同一个计数器
Δtobs
从采图到提交请求之间的纳秒数
f
动作频率（Hz）——双臂 PiPER 上是 30
T
模型实际返回的行数

c < T 才接受，然后执行第 c…T−1 行。否则整个回复都过期了：立刻丢弃并重新请求，而不是等下一次自然触发。

而什么时候去要下一个 chunk，来自实测延迟，不是来自某个人看着顺眼的数：

ntrigger= min(H−1, q0.95+m + (p+τ)⏟ 仅 blend )
ntrigger
队列剩到这个深度就发下一次请求
H
模型 horizon 的行数
q0.95
最近 32 次回复的实测往返延迟 95 分位
m
设计余量——默认 1 步
p
preserve 步数——我们选的，不是测出来的
τ
transition 步数——只在 blend 模式下计入

值得刻进脑子里的区别：q 是我们测出来的，p 和 τ 是我们定的。preserve = 2 不代表"GPU 花了两步"，它代表运行时决定在替换到达之后，再多信任两行对齐过的旧目标。把这两者混起来，你就会开始凭手感调延迟预算——8 月 12 日大致就是这么回事。

下面是完整的一个周期。拖滑块——有意思的地方是看哪些行换了主人。

我们的 RTC 不是什么

客户端 RTC 对已经完成的 action chunk 做对齐，以及可选的混合。就这些。previous-action 条件、冻结扩散步、梯度 guidance——那些是模型后端的能力，打开预取一个都不附送。

它们也可以被训练进去；我们 store 里就有一个 bundle 直接叫 …-trainrtc-d0to6-v1。那是那份权重的性质，和 real_world/rtc.py 做的事仍然是第三件独立的事。我们见过这三样在同一场对话里都被叫做"RTC"。

04

平滑做得越多，看起来越不平滑

上面那个故事里，真正让我意外的是这部分。

我们拿它跟 DAgger-GR3——上一代的 stack——做了对比，而所有人都同意后者感觉更顺。它做的平滑更少，少很多。它会完整执行一整个连贯的 chunk，大约 1–1.7 秒的同一份计划，然后才去要下一个。而且它允许每个在线关节步 0.15 rad，我们是 0.10。

所以更新的、滤波更多、限制更紧的这套，看起来更差。

说出口之后我觉得这不算什么悖论，但我们花了挺丢人的一段时间才把它说出口：一套更频繁替换轨迹、然后又把自己追赶的尝试裁掉的系统，会比一套干脆认准一份计划的系统看起来更不平滑。每一次重规划都是一次跟自己意见不合的机会。每一次裁剪都是机器人离它正在追的目标又远了一点。

我们当时建议的下一步不是"放松安全上限"，而是 RTC_TRIGGER_STEPS=16——让相邻两次接受之间执行约 14 行连贯动作而不是 6 行——所有限制原封不动。

我们真正在跑的处理器有哪些

这里我想诚实一点，因为很多讲 VLA 部署的文章会把所有轨迹技巧都列出来，好像它们全都在用。在我们一个通过资格验证的部署里，真正开着的只有三样：

  • 模型关节上的一阶低通。双臂 PiPER 默认开，α = 0.6。
  • RTC 对齐，以及可选的有界混合。GR3 和 Astribot 用 align；blend 需要显式打开。
  • 五次最小 jerk 分段轨迹，用于 Prepare、Home 和数据集位姿过渡。

PCHIP 重采样和 chunk QP 在 real_world/output.py 里都有实现。两个都默认关闭，GR3 提交的默认值就是 GR3_CHUNK_SMOOTHING=off，我们从来没有把它们中的任何一个验证到硬件上。我提这两个主要是为了：你读那个文件的时候，别以为它们在承重。

低通，以及所有人都会搞错的那部分

yt= yt−1 +α ( xt− yt−1 ) , 0<α≤1
yt
本 tick 真正下发的滤波后目标
yt−1
滤波器自己上一次的输出——这就是状态
xt
本 tick 传进来的协调后目标
α
双臂 PiPER 上是 0.6。越小越平滑，也越滞后

这个滤波器是有状态的，而这个状态就是全部故事。如果目标停在 1.0、输出读数是 0.5，那不是"目标被削小了"——后续更新会继续收敛到 1.0。理论上没问题。但在有限长的 action chunk 上，重规划通常在收敛之前就到了，所以真实行为更接近"永远只走到 60%"。这不是任何人想要的。

四个接线细节，每一个都是我们弄坏之后学到的：

  • 它在 RTC 协调之后跑，只作用于模型关节。
  • 在 Start、接管、HOLD、反馈失败或 generation 变化之后的第一步，它用新鲜的实测关节重新初始化。
  • 普通的 chunk 替换不会重置它。在那里重置，等于把这个滤波器本来要抹平的接缝又放回去。
  • 专家动作和两个夹爪宽度完全绕过它。夹爪上的相位滞后会错过抓取时机，没有任何 α 能修好这件事。

未滤波的目标先过一次检查，滤波后的目标在 owner 写 SDK 之前再过一次最终安全门。滤波不是绕过那道门的方式。

05

把起始位姿弄得更对称，反而更糟

同一周，另一个谜。我们注意到 GR3 在 episode 开始时两条手臂不齐——正运动学算出来，左手比右手前伸约 24 mm，左手食指尖高约 8 mm。有点丑。显然值得修。

于是初始化 profile 从 …start-v5-claude-elbows 换成了 …start-v6-bilateral-fk，把两条手臂对称化，若干关节最多移动 0.084 rad（4.8°）。

几何变好了。行为变差了。

原因，在我们停止盯着机器人看、回去看数据之后：v6 是一个算出来的位姿。它是一个双臂 FK 解。它不是训练 episode 里任何一帧。所以 checkpoint 拿到的第一帧观测，是一个它从没见过的轮廓——任务还没开始，它就已经在解一个分布外问题了。它把这个表现成了犹豫，而我们花了一阵子去怪延迟。

可以推广的那一条，是我最希望别人带走的，因为它同时也否掉了一个听起来很聪明的方案：逐关节取中位数有完全相同的缺陷。每个关节的值单看都很典型。组合起来却可能是一个在零个 episode 里出现过的身体构型。一个用健康零件拼出来的缝合怪。

改成从数据里取位姿

我们现在在 PiPER 上的做法是挑真实录下来的帧——每条 prompt 12 个 follower-state medoid，取自真实的训练候选 episode。筛选规则很挑剔，而每一条都是因为放松过之后出过坏位姿：

  • 锚点取在检测到的持续关节运动起始之前 8 帧（30 Hz 下约 267 ms）——示范者即将发力的那一刻。
  • 严格限制在 episode 的前 22%。绝不取中段，绝不取尾部。
  • 后面至少还有 120 帧且有显著的后续运动，保证这是一个真正的"开始"而不是一次停顿。
  • 远离任何终止状态。终止帧和完成后的帧被 schema 直接禁止。
  • 库里没有覆盖的 prompt 直接 fail closed，而不是退化成某个通用 home 位姿。

运行时，唯一的硬件 owner 只接受来自 SHA-256 绑定库的 pose id，然后自己独立重新推导关节限位和最大位移，才会执行任何东西。UI 从不发裸的 12 维目标。如果当前位置无法直达候选，owner 会经由声明的 clear/home 位姿拆成两段有界轨迹，每段下发前检查插值法兰高度——如果这条有界路径仍然不安全，它就 fail closed，而不是去开某个门。

诚实地说这件事买到了什么

我们现有的示范几乎都从同一个地方开始。所以这些 medoid 是真实的早期 episode 变体——它们不是一个多样化的起始分布，我也不想过度包装它。真正的起点多样性意味着去采 varied-start 示范。再聪明的筛选规则，也造不出从未被记录过的覆盖。

06

拿自己采的纠正数据微调，模型更差了

这一个的起点是机器人领域最让人泄气的一句话："拿这份 DAgger 数据微调，效果反而更差。"

我们去找那个 bug。没有那个 bug。有六个，而且它们会叠加。

这些都在更早的 GR3 recorder 里，现在已经修掉了。我还是把它们列出来，因为这些失败的形状会在每一次新采集里重现，而且六个里有四个，你不主动去找就根本看不见。

  1. 后续的纠正被悄悄丢掉。recorder 在每次 save 或 discard 之后清空自己的 episode_index，而没有 index 就拒绝开始录——但控制器只在模型 episode 开始时发一次 index。所以一个 episode 里第一次接管录得好好的，第二次没有。我们的数据集被系统性地偏向"第一次纠正"，而那通常是最没意思的一次。
  2. label.valid 被污染。重复的接管状态消息会发出一个 label_valid=false 的默认决策。原始采集里：88,825 个 false 对 77,354 个 true，约 20% 的对齐专家动作，最近的 validity 样本是 false。我们的严格转换器没有天真地消费那条流，所以 bundle 幸免了——但任何按最近时间戳 join 的东西都会把这个错误整个继承下来。
  3. "成功"只表示操作员按了 save。不表示玩偶最后落在了任何特定的地方。
  4. 我们只录了接管片段。没有紧邻其前的模型失败，也没有其后完成的恢复。孤立的纠正，任务上下文被切掉了。
  5. 数据配比严重过采样了纠正。新 DAgger 数据占每个 batch 64 中的 28——43.75%——而到 step 4000 时每个片段大约被看了 8.3 次。短促而显眼的纠正动作，会盖掉父模型原本已经具备的长程成功行为。
  6. 六段录制里，安全限幅过的动作配着未裁剪的标签。在严格重建里被隔离了。

给个量级：严格数据集最后是 22,996 帧 / 13,448 条有效 H32 query。后来的 hybrid bundle 报告 211 个 DAgger 片段、22,742 帧、16,201 条有效 query，配比大约 40% DAgger / 60% replay。

能修掉大部分问题的那件事：按控制 tick join

相机跑 30 Hz。硬件控制器跑 60、100 或 200。GR3 上我们测到机器人状态 ≈30.29 Hz，专家动作 ≈99.88 Hz，对齐通常在 5 ms 以内。这些是很漂亮的数字。它们仍然不足以支撑按最近时间戳 join，因为"最近"可能悄悄跨过一个接管边界，或者取到错误的 validity 心跳。

所以身份改成因果分配：唯一的 owner 只在 SDK 下发成功之后才分配 control_tick_id。这次下发对应的已执行动作、被选来源、标签有效性和被接受的证据，共享同一个 id。Router 侧的提议 id 单独保留为 decision_control_tick_id，并且被明确规定不作为硬件动过的证据。任何缺失、冲突，或者只能靠时间戳回退才能 join 的区间，一律进隔离区——绝不猜成有效标签。

这就带出另一件值得分清楚的事。这条流水线里有五个不同的张量，大家都管它们叫"动作"：

一行可训练，当且仅当 source = EXPERT、接管参考有效、安全有效，并且 label.valid = true。标签本身是 action.expert_aligned_unclipped_robot——操作员对齐之后的意图目标。

这里有个显而易见的问题：为什么用未裁剪的意图训练，而不是机器人实际做的？因为当机器人执行的基本就是那个目标时，意图是更干净的信号。但当安全层实质性地改动了它，用意图训练就等于教出一个从未在环境中被示范过的行为。那六段被隔离的录制就是这种情况——注意那个动词：隔离，不是修复。被污染的标签没法被反推回一个好标签。

接管对齐，简单说

在接管的上升沿，我们恰好一次地固定两个构型——机器人的实测构型和专家设备的构型。之后的一切都是相对的：

aexpert(t)= q0robot + ( qexo(t) − q0exo )
aexpert(t)
对齐后的专家目标，也就是训练标签
q0robot
接管上升沿那一刻机器人的实测构型
qexo(t)
外骨骼当前的构型
q0exo
同一上升沿时外骨骼的构型

没有它，你一接管，机器人就会朝外骨骼那个毫不相干的绝对构型跳过去。有了它，转移过来的是操作员的运动——那本来就是你想录的东西。

一个变成了数据集属性的运行时常量

这块我最喜欢的小恐怖故事。QNexo adapter 的默认值是 EXO_WAIST_YAW_SPEED = 0.1，adapter 里再除以 100，得到每次更新 0.001 rad——在设计的 100 Hz 环路下大约 0.1 rad/s。这非常慢。操作员注意到了。

凭手感把它提到 0.5，遥操作体验好很多，同时也改变了下一个 checkpoint 将要学习的纠正分布。因为模型预测的是未来目标位置而不是速度，更慢的标签只是意味着在 H32 horizon 上更小的目标变化量。而当同样的视觉和状态情境同时带着快的预训练标签和慢的 DAgger 标签，损失会很愉快地把它们平均成犹豫。

正确的标定做法是从原始 episode 里算逐关节的速度和加速度分位数，然后去匹配它们。另外：不要试图靠给 yaw 值乘一个系数来修复旧的慢数据。那会破坏时间上以及手臂／腰部之间的协调，产出的标签单看都合理、合起来不可能。

还有，请把视频按视频编码

数值、事件和对齐元数据属于 Parquet。相机帧不属于，而且这个账算得根本不接近。一个真实的 30 Hz 双臂 PiPER episode，三路 1280×720 RGB 以 Parquet 数组存储：

相机流：4.59 GB。全部 14 条数值／事件／标签流加起来：0.59 MB。episode 时长：52.6 秒。

这正是你能预测出来的结果——3 × 1280 × 720 × 3 字节是每帧 2.76 MB，乘 30 Hz 是 82.9 MB/s，乘 52.6 秒是 4.36 GB。对带相机噪声的 uint8 数组，Parquet 压缩基本没有作用，所以图像最后大约是其他一切的 7,700 倍，而且没有任何压缩设置能改变这个比例。编码成 H.264 MP4，把 帧 → 时间戳 → control_tick_id 的映射留在表格元数据里，因果 join 就仍然成立。

07

最不性感的解法：一个 checkpoint 一个文件

上面这些没有一件是有趣的研究。但每一件都要花掉真实的天数。真正让这些事不再疼的东西很无聊：让每个问题都恰好有一个文件能回答。

我们最后收敛到的规矩是：一个新 checkpoint 需要的应该是一份 descriptor，而不是 launcher 里的一个新分支。launcher 需要知道的关于某个模型的一切都是数据。launcher 本身里没有任何 if model == …。

policy/<POLICY>/deployments/<deployment>.yml  ·  节选 
bundle:                          # 身份与不可变性
  default_path: model-store/models/<policy-family>/<checkpoint>
  required:     [checkpoint/model.safetensors, contract.json]
  verifier:     policy/<POLICY>/verify_bundle.py

policy:                          # 时序合同，与 contract.json 一致
  action_frequency_hz:   30
  action_horizon:        32
  default_execute_chunk: 16
  default_execute_mode:  auto    # 跟随模型的 execute_prefix_steps

observation:
  camera_profile: camera_profiles/piper-x-dual-rgb-1280x720-30.yml

server:
  default_mode: managed          # launcher 拥有 PolicyServer 的生命周期

tasks:
  catalog_path: contract.json    # 权威在 bundle，不在这个文件

intake:
  provider:       aliyun_oss
  expected_bytes: 7245891272     # 精确大小，会被校验

qualification:
  verifier_args: [--full-manifest]
  tests:         [ tests/test_inference.py, …, tests/test_pi05_piper_dagger50_h32_v1.py ]

从上往下读一遍，你就能回答：哪份权重、怎么校验、什么频率、用哪些相机、怎么服务、走哪张 graph、用哪些 prompt、从哪来、由哪些测试证明。这就是全部意图。

然后两条命令覆盖整个生命周期——onboard 负责首次 intake，qualify 负责已安装的运行时。同一套 stage 机器：把每个文件对着三份 manifest 校验（本地哈希、本地 manifest、发布方 manifest），准备隔离的模型运行时，跑 descriptor 自己的测试列表，绑定一个空闲的 loopback 端口，启动 managed server，用一份符合合同形状的合成观测探测它、断言 30 Hz 下有限的 [32,14]，最后做一次禁写的 launcher dry run。产出是一份 JSON 报告和逐阶段编号日志。

为什么那句话里有"空闲的 loopback 端口"

因为看到 address already in use 时，最诱人的做法是把占着端口的东西全杀掉，而我们见过这么干的下场。正确做法是找出监听者并校验它的 WebSocket HELLO：部署身份一致就显式复用；不一致就只停 launcher 自己拥有的那个进程。

一个来自别的 checkpoint、恰好在对的端口上应答的野生 server，会自信地给你喂一整个下午的错误动作，而你的日志里不会有任何一行看起来可疑。

这一切底下是一条我们严格得有点不讲道理的不变量：有且只有一个进程可以调 SDK。模型候选和专家候选都只是提议。router 选来源，机器人自有的门放行或 HOLD，owner 写入，recorder 旁观一切、而且永远没有写的能力。

VLM 站在这一切之上，而这个位置是刻意的。任务选择和恢复推理是慢速、会出错的；运动控制是硬实时的。把它们直接接在一起，一次两秒的语言模型往返就会跑进一个 33 毫秒的控制环里。

所以我们的 supervisor 不是第二张 Dora graph。它是一个独立进程，只通过带认证的 loopback API 通信，只能发出 checkpoint 那份精确的五条 prompt 目录里的条目（目录之外一律 fail closed），而且从不发关节目标。它的 rollout 预算在唯一写者处按实际收到的 model action 计数——不看墙钟，也不信它自己的计数。rollout 一旦开始，实时路径完全不变，VLM 不在里面。

08

那些无聊的答案，和我们不再混着用的词

不是每个谜都很深。下面这些是我们现在会先查的，大致按"最后发现真是它"的频率排序。

症状我们很想做的事通常真正的原因
机器人完全不动怪推理，加平滑ENABLE_WRITE=0。频率高得惊人。然后才是生命周期状态、控制器模式、新鲜的 SDK 反馈、实际下发计数。
反馈报 0 Hz调低新鲜度阈值CAN 身份、供电、控制器模式。放宽的看门狗造不出缺失的反馈——它只是让你去指挥一台你看不见的机器人。
能加载但行为随机以为形状对上了就是兼容归一化统计量、tokenizer、相机键、状态字段顺序、单位、动作逆变换。对着 bundle 比，别对着记忆比。
左右反了把 UI 标签换到看起来对为止顺着序列号 → instance 角色 → graph 输出 → 观测键 → 训练相机角色追一遍。然后去相机前挥手。
相机启动后卡死把期望的 USB 3.2 放宽到 2.1带宽、hub、线缆。frame-number 缺口才是测量值；放宽身份校验造不出帧。
停—动—停把混合加长队列饥饿、被拒的替换、迟到的结果。加长混合只会更糟。见 §3。
动作过激把所有平滑器一次全加上把原始逐步速度和训练分位数比较，然后只加一个能归因的处理器。
数据集巨大调高 Parquet 压缩数值走 Parquet，相机走 MP4。比例约 7,700:1，压缩设置只是噪声。

这些背后的做法是同一个：不要从最终的视觉症状开始调。跟着一条观测和一个动作穿过整个系统，找到数值第一次不再符合它的合同的那个边界。五个问题，按顺序——模型收到了什么，它返回了什么，运行时调度了什么，owner 接受了什么，物理上发生了什么。大多数争论的发生，是因为有人从第一个问题直接跳到了第五个。

五组混起来之后让我们付出真实时间的词

这里每一组，一旦在某个人脑子里或某份文档里塌缩掉，都会产出一类特别难找的 bug——因为所有相关的人用的是同一个词。

  • 当前 vs 历史。当前代码才是事实来源。八月的一段聊天记录，是关于一个此后可能已经变了的系统的案例。§6 里的 recorder bug 是真的，也已经修了；能迁移的是那些失败的形状。
  • 客户端 RTC vs 模型原生 guidance。上面说过了。开预取不会给你任何关于条件化的东西。
  • 原始 vs 协调后 vs 已执行。三个不同的张量。一旦开了混合，协调后的流就不再逐字节等于原始回复，而在证据链路里把它标成"raw"，会污染它下游的一切。
  • 原始 episode vs 派生视图。完整录制保留上下文；训练视图是它的一个严格投影。两个都留着，不可变，这样一个标注决定可以被重新推导，而不是拿来吵架。
  • 资格验证 vs 移动授权。报告全绿证明的是 restore、合同形状、服务一致性和一次禁写 dry run。它对任务成功率什么都没说——bundle 自己的 evidence_scope.does_not_establish 就明说了。让真机动起来，需要一次显式的 live-run 请求、写授权门，以及一个手放在急停上的人在场的监督 canary。

我们现在落在哪里

我不觉得这里面有什么新东西，如果有我反而会有点意外。但它非常一致：每一次部署变得玄学，答案都在数据集里——而每一次我们改成在运行时层去修它，我们都把下一个 checkpoint 弄得更差了。

从数据里采起始位姿。从数据里测专家速度。从数据里恢复相机角色和时序。把动作语义追溯回那个生成数据的变换。

训练合同显然修不了一根断掉的 CAN 线，也修不了一台坏相机。它做的是：不让硬件故障被误判成模型故障，也不让一次分布外部署被运行时小技巧"修好"、然后悄悄毒化下一轮训练。

还有不少我们没有好答案的东西。我们的示范里没有真正的起始位姿多样性，而再聪明的 medoid 筛选也造不出从未被记录过的覆盖。我们也没有一个有原则的方法去选 DAgger 的 replay 比例——40/60 是"有效"的那个，不是推导出来的那个。而且我们仍然没法从单次 rollout 判断，一个 checkpoint 是今天状态不好，还是学到了某种微妙的错误。如果你对其中任何一个有好答案，我是真的想听听。
